# review-proof-prs — 검증·제출 게이트

발굴된 후보(가설)를 받아 **리뷰를 뚫는 PR**로 굳힌다.

## 왜

발굴은 가설일 뿐이다. PR이 리뷰를 뚫으려면 세 관문이 필요하다: **(a) 재현**으로 진짜임을 증명하고, **(b) 독립 렌즈들**이 못 깨야 하며, **(c) 본문**이 AI티·과장 없이 근거로 서야 한다. 하나라도 건너뛰면 "그럴듯하지만 틀린" 것이 새어나간다.

## 실행 순서 — 아래 절 번호는 주제 묶음이지 실행 순서가 아니다

```
0 승인 경계 → 1 재현(RED) → 2 최소 수정(GREEN) → 3 진짜 실패하는 테스트 → 3-1 회귀 대조
  → 4A 코드 렌즈(0·2, 본문 없이)
  → 5 본문(분량 게이트 → AI티 게이트 → 기계 무결성 검사)
  → 6 문외한 설명(이해 게이트)
  → 4 렌즈 게이트 → 영수증   ← 본문이 확정된 뒤여야 렌즈 10(본문)이 검사할 대상을 갖는다
  → 7 landscape 재확인 → 8 제출(사람 승인)
```

렌즈 뒤에 본문을 한 글자라도 고쳤으면 렌즈를 다시 돈다 — 영수증이 본문 해시로 묶여 있어 배선이 그것을 강제한다.

## 0. 사람 승인 경계

실제 push·PR·제출은 **외부로 나가고 되돌리기 어렵다**. 반드시 사람의 명시적 승인을 받고 실행한다. 로컬 커밋·재현 하네스·렌즈는 승인 없이 돌린다. "커밋해뒀고 push는 대기"가 정상 상태다.

## 1. 재현 먼저 (RED/GREEN)

**재현 없이는 수정 없다.**

- **RED**: 미수정 코드에서 버그를 재현하고 *실제 출력*을 캡처(에러 로그·행 수·응답 바이트).
- **GREEN**: 최소 수정 후 같은 시나리오가 해소됨을 *실제 출력*으로 확인.
- 재현이 안 되면 버그가 아니다. **여기서 non-bug를 죽인다.**
- **서브에이전트·워크플로가 낸 RED/GREEN 을 그대로 쓰지 마라.** 그건 가설이다. 본문에 실릴 출력은 내 손으로 다시 낸다.
- 하네스는 스택마다 다르되 원리는 하나 — **실제 사용 경로를 태워 RED/GREEN을 real output으로 대조**. 스택별 레시피: **[references/red-green-harness.md](references/red-green-harness.md)**.
- **테스트를 짜는 것과 프로그램을 돌리는 것은 다르다 — 빌드해서 실행한다.** 판정 전에 세 줄을 확보한다: 빌드 명령과 소요 시간, 실행한 명령과 실제 출력, 이 기계가 못 돌리는 부분. 에뮬레이션(`docker run --platform ...`)은 정확성만 믿고 성능 수치는 못 쓴다.
- **짝으로 나뉜 API(만들기 encode / 확인하기 matches)는 양쪽을 다 태워야 수정 방향이 정해진다.** 한쪽만 보고 "문서가 틀렸다/코드가 틀렸다" 를 정하지 않는다.
- **기준선은 `upstream/<base>` 실물이다.** 로컬 `main` 은 내 변경을 품고 있을 수 있고, 포크는 뒤처질 수 있다 — 코드는 `git show <원격ref>:<경로>` 로 읽고, 착수 전 `git rev-list --count origin/main..upstream/main` 이 0인지 본다. 리비전을 옮긴 빌드는 clean 부터.
- **동시성 후보**는 TLA+/TLC 로 인터리빙을 먼저 스펙화할 수 있다. 단 그건 가설 정제다 — 반례를 실제 스레드 테스트로 옮겨 출력을 캡처해야 RED다.

## 2. 최소 수정

root cause만, 주변 코드 컨벤션에 맞춰, 가장 작은 diff로. "온 김에 리팩터" 금지 — 범위가 커지면 거절 확률이 오른다.

**수정이 연달아 "직전 수정이 만든 문제" 를 막는 모양이면 멈추고 설계로 돌아간다.**

1. 목적을 한 문장으로 쓴다. 안 써지면 아직 만들 때가 아니다.
2. 그 안의 결정을 나열하고 **각각을 무엇이 정하는지** 적는다. 둘 이상을 같은 것이 정하면 그게 결합이다.
3. 결합을 금지하는 테스트를 남긴다.

설계가 맞으면 코드가 줄어든다. 늘어나면 설계를 의심한다.

## 3. 실제로 실패하는 테스트

테스트는 **실제로 등록되고 실제로 실패**해야 한다. 검증법: **수정을 도로 빼서 RED가 뜨는지 확인**하라. 안 뜨면 그 테스트는 가짜다(top-level IIFE 처럼 러너에 등록조차 안 되는 테스트가 있다).

## 3-1. 회귀는 "같은 리비전" 과 대조한다

전체 스위트가 원래 빨간 저장소가 흔하다. **기준선을 따로 떠라.**

- **같은 워크트리에서 수정만 토글한다.** 고친 줄을 주석 처리 → 전체 스위트 → 되돌림 → `touch`. 늘어난 실패 수가 **내가 추가한 테스트 수와 정확히 같아야** 한다.
- 별도 워크트리 기준선은 리비전이 다를 때만 — base 가 다르면 테스트 총 개수부터 달라 비교가 무의미하다.
- **토글에 git 을 쓰지 마라.** `stash`/`checkout` 은 검증 인프라(`skipTests` 해제한 pom 등)까지 되돌려 "테스트가 안 돌았는데 EXIT=0" 인 가짜 판정을 만든다.
- 보고 형식: `기준선 100/실패2/오류10 → 수정후 102/실패2/오류10, 늘어난 2건이 내 테스트` (예시 수치).

## 4. 렌즈 게이트

렌즈는 **본문이 완성된 뒤**에, **본문·diff·커밋 메시지**에 대고 돌린다. 본문 없이 코드에만 돌리면 렌즈 10(본문)은 검사할 대상이 없다. 순서는 **코드 확정 → 본문 → 윤문 → 렌즈 → 영수증 → 제출**이다.

**에이전트 하나가 여러 축을 보는 것은 렌즈 하나로 친다.** 독립성이 렌즈의 값이다.

### 4A. 코드를 먼저 굳히고 본문을 한 번만 쓴다

본문을 쓰기 전에 렌즈 0·2 를 코드에만 한 번 돌린다([assets/lens-prompt-code.md](assets/lens-prompt-code.md)). 이 판정은 영수증에 못 쓴다 — 목적은 코드 결함을 본문보다 먼저 죽여 본문·윤문·렌즈를 한 번씩만 돌게 하는 것이다.

### 렌즈

| # | 렌즈 | 보는 것 |
|---|---|---|
| 0 | 전제 파괴 | 문제가 실재하는가 — **항상 돈다** |
| 1 | 회의론/의도 | 의도된 동작·문서화된 계약 아닌가 |
| 2 | 정확성 | root cause를 고치나 |
| 3 | 엣지 | 경계·널·빈값·최대치 |
| 4 | 부작용 | 다른 경로·형제 기능을 깨지 않나 |
| 5 | 메커니즘/E2E | 재현이 실제 사용자 경로인가 |
| 6 | 검증 | RED/GREEN이 진짜 증명인가 |
| 7 | 컨벤션 | 코드·프로젝트 관례 |
| 8 | 수용성 | 범위·정책상 받을 만한가 |
| 9 | 완결성 | 놓친 형제 결함·미검증 주장 |
| 10 | 본문 | 사실 정확성·AI티·과장 |

정의는 `lenses/` 파일 하나씩이고, 공통 규칙은 `lenses/_guardrails.md` 다. `<플러그인 루트>/scripts/build-lens-agents.sh` 가 이것으로 쓰기 도구가 막힌 에이전트 정의 `agents/lens-<N>.md` 를 만든다. **렌즈 프롬프트를 손으로 쓰지 마라.**

**렌즈 0(전제 파괴)은 규모와 무관하게 항상 돌린다.** 나머지 렌즈는 "수정이 옳은가"를 묻느라 전제를 참으로 놓는다. 전제가 거짓이면 게이트 전체가 통과시킨다. **집계는 다수결이 아니다** — 하나라도 막으면 막힌다. **전원 SUBMIT-OK + 모든 CONCERN 반영**이어야 제출한다. NIT 은 사유와 함께 남겨도 된다.

### 레벨과 영수증

규모는 작업에 비례하되 **선언한다** — 판정문 맨 위에 `LEVEL: <이름>`, 각 렌즈 `LENS: <번호> <판정>`, 렌즈가 직접 잰 `BODY-SHA:`, 전체 `VERDICT:`. 레벨별 필수 렌즈·정족수는 **[references/lens-levels.json](references/lens-levels.json)** 이 정본이다.

```bash
# <플러그인 루트> = 이 스킬 디렉터리의 두 단계 위 (skills/review-proof-prs/../..)
<플러그인 루트>/scripts/lens-record.sh --level essential <본문.md> <렌즈판정.md>   # 본문 해시로 영수증 발급
<플러그인 루트>/scripts/outbound-check.sh <본문.md> <근거.txt>                    # 주장 후보·근거 줄 수·영수증 확인
```

`lens-record.sh` 는 렌즈가 읽은 본문 해시가 지금 본문과 다르면, 필수 렌즈가 빠졌으면, CONCERN 이 미반영이면 거부한다. 본문을 고치면 영수증이 죽는다.

### 워크플로로 돌린다

`assets/lens-gate.js` 에 카드 매니페스트를 넘기면 레벨대로 병렬 디스패치하고 집계한다. 고정 인자는 `assets/lens-args.sh` 가 실물에서 뽑는다. 디스패치 방법·격리·3점 검사·운용은 **[references/ten-lens-dispatch.md](references/ten-lens-dispatch.md)**.

- **2라운드부터는 델타다.** 바뀐 것만 겨냥하고 재현·인용 전수 대조를 반복시키지 않는다([assets/lens-prompt-delta.md](assets/lens-prompt-delta.md)). 단 렌즈는 그 레벨 전원을 다시 돌린다.
- **라운드 상한: 3라운드를 넘기면 진단이 먼저, 6라운드가 끝.** 4라운드 전에 원인을 한 줄로 적는다 — `같은 지적 반복`(고치는 방향이 틀렸다) · `내 수정이 새 오류`(정정을 줄인다) · `새 결함`(코드가 덜 굳었다). 6라운드에도 안 닫히면 멈추고 사람에게 올린다.
- **렌즈 앞에 기계 검사를 세운다.** 인용 좌표 실재, 출력 인용의 원문 일치, 요약 숫자 대 나열 건수, 커밋 author 주소처럼 사람 판단이 필요 없는 것은 스크립트로 먼저 죽이고, 렌즈 프롬프트에 "기계 검증됨, 재확인 금지"를 적는다.
- **"~가 없다"류 부정 판정은 외부 조치 전에 내 손으로 재현한다.** 판정 기준은 "몇 명이 말했나"가 아니라 "내가 재현했나"다.
- **삭제 PR 에서는 코드 밖 잔재를 따로 훑는다** — 아키텍처 문서·README 모듈 목록·CHANGELOG·로케일 키·CSS·아이콘·픽스처.

## 5. 본문

글쓰기 규칙 정본: **[references/writing-rules.md](references/writing-rules.md)**. 스켈레톤: **[assets/pr-body-template-ko.md](assets/pr-body-template-ko.md)** / **[assets/pr-body-template-en.md](assets/pr-body-template-en.md)** — 저장소 템플릿이 있으면 그것이 우선이다.

- **게이트는 둘이고 순서대로 다 돌린다.**
  1. **분량 게이트("없으면 죽나")** — 뺐을 때 리뷰어 판단이 달라지지 않는 말은 전부 쳐낸다. AI 티 제거 도구는 문체를 고치지 분량을 줄이지 않는다.
  2. **AI 티 게이트** — 영어 본문 → `humanizer`, 한글 본문 → `humanize-korean`. 건드리면 안 되는 것(코드블록, 체크박스, 경로·식별자·커밋해시·줄번호, 터미널 출력, 한정어)을 명시한다.
- **웹 입력칸에 들어갈 본문은 문단당 한 줄.** 하드랩은 코드블록 안에서만.
- **`$` 프롬프트를 단 블록은 실제 출력이어야 한다.** 다듬고 싶으면 명령을 다시 돌려 붙이고, 지울 곳은 `[...]` 로 표시한다.
- **테스트 증거 형식은 저장소 문화에 맞춘다.** 머지 PR 본문의 증거 형식을 표본으로 확인하고 복제한다.

### 윤문 뒤에는 기계 무결성 검사

윤문은 본문을 다시 쓴다. 게시 전에 원문과 기계 대조한다 — 코드블록 바이트 동일, 체크박스·헤딩 동일, 식별자·숫자 출현 횟수 동일, 최장 줄 길이(하드랩), 금지 어휘. 에이전트가 쓴 본문은 손으로 쓴 본문보다 결함 밀도가 높으니 윤문 결과를 사실 게이트로 한 번 더 본다. **사실 게이트는 렌즈다.**

## 6. 문외한 설명 — 이해 게이트

PR 본문 옆에 **아무것도 모르는 사람이 봐도 알 수 있는 설명**을 따로 쓴다. 요청받기 전에 기본으로 낸다.

- **(a) 이해 게이트.** 쉬운 말로 못 쓰면 메커니즘을 덜 이해한 것이다. 막히는 지점이 곧 안 판 곳이다 — 막히면 제출하지 말고 판다.
- **(b) 사람 책임의 근거.** 소유자가 이해 못 하는 것에 이름을 걸 수는 없다.

쓰는 법: 도메인 지식 0을 가정한다 · 일상 비유를 하나 쓴다 · 실측값을 그대로 보여준다 · "왜 실수라고 단정하나"(문서·형제 경로·도입 커밋)를 넣는다 · 누가 영향받나로 끝낸다(조용히 비는 부류인지 밝힌다). 비유는 PR 본문에는 넣지 않는다.

## 7. 제출 직전 landscape 재확인

push 직전 업스트림을 다시 본다: 이미 고쳐졌나? 관련 PR이 머지·클로즈됐나? 실권 메인테이너와 머지 주기는?

- **후보 착수 첫 단계도 이슈 재검색이다 — 소스를 읽기 전에.** 심볼명·에러 메시지·기능명 세 갈래로 `gh search issues` 부터.
- **후보가 확정될 때마다 처음 뽑은 PR·이슈 목록으로 돌아가 제목을 하나씩 대조한다.** 열린 PR·최근 머지·브랜치 이름까지.
- **반대 방향 이슈가 같이 열려 있으면 그건 설계 논쟁이지 버그가 아니다.** 기존 이슈에 실측만 얹는다.
- **base 브랜치는 머지된 외부 PR의 분포로 정한다.**

```
gh pr list -R O/R --state merged --limit 200 --json baseRefName,author \
  --jq '.[] | select(.author.login|test("bot")|not) | .baseRefName' | sort | uniq -c
```

- **새 저장소에 첫 제출 전**, 최근 머지된 외부 PR 5~10건과 거절 PR 댓글을 해부해 "머지되는 형태"(diff 크기·이슈 선행 여부·테스트 동반·타깃 브랜치·서명 규약)를 데이터로 뽑고 복제한다. 릴리즈 노트·Discussions 도 소스다.
- **테스트가 전부 깨지면 내 수정을 의심하기 전에 CI 워크플로가 무엇을 체크아웃·설치하는지 읽는다**(`submodules:`·`node-version-file`·설치 명령).

## 8. 제출

포크로 push → PR 생성. **사람 승인 후에만.**

- **커밋 메시지도 본문과 같은 게이트를 받는다.** 본문을 고칠 때마다 메시지에 같은 주장이 있는지 확인한다.
- `git commit --amend` 는 본문 해시를 안 건드리므로 렌즈 영수증이 살아 있다. 포크는 `--force-with-lease` 로 갱신한다.
- 커밋 author·committer 주소는 전역 설정 그대로. 푸시 전 `git log -1 --format='%an <%ae>'`.

## 함정 카탈로그

- **hollow test** — 수정을 빼도 통과하면 가짜 테스트.
- **shared-clone 오염** — 리뷰어·검증은 read-only/격리로.
- **RED 는 "컴파일되고 단언이 실패"** — 컴파일 에러 빨강, 주석 줄을 잡은 치환, 층이 어긋난 테스트는 가짜 RED다.
- **`git stash` 가 아무것도 안 잡았는데 GREEN 으로 읽지 마라** — 이미 커밋한 파일은 stash 대상이 아니다.
- **GREEN을 보기 전에 커밋·푸시하지 마라.**
- **발굴 메모는 증거가 아니라 가설이다** — 착수 전에 지목된 코드가 살아 있는지 본다. 숫자도 다시 센다.
- **"이러면 이렇게 된다" 가 모든 구성에서 참인지 확인하라** — 소수 구성에서만 참이면 양쪽을 다 개선한다는 논지로 바꾼다.
- **테스트를 돌린 뒤에는 `git status` 를 본다** — 추적 중인 출력 싱크·롤링 로그가 커밋에 쓸려 들어간다.
- **커밋 계보는 ±양쪽으로** — `+` 줄만 grep 하면 리워딩을 신규 추가로 오인한다.
- **범위 방어는 전수 스캔 + 스캐너 자가검증** — 스캐너를 수정 전 상태에 돌려 그 버그를 잡는지 확인한다. 스캐너를 만들면 그것이 놓치는 형태를 먼저 센다.
- **BUILD SUCCESS 는 "내 테스트가 돌았다" 가 아니다** — `Tests run:` 줄에 기대한 클래스명이 있는지까지 본다.
- **물려받은 제약은 내 측정이 아니다** — "비싸다/불가능하다" 를 근거로 버리기 전에 한 번 돌려본다.
- **`// TODO` 가 붙은 지점은 PR 이 아니라 이슈다.**
- **"검사기가 허술하다" 는 API 한계일 수 있다** — 더 나은 검사 수단이 있는지 먼저 본다. 없으면 버그 수정이 아니라 설계 변경이다.
- **손으로 스캐너 짜기 전에 코드 그래프 도구를 써라** — 호출자·영향범위는 그래프가 답한다. 정규식은 그래프가 못 보는 것(문자열 키, 주석 속 계약)에만.

### 게이트 순서 — 싼 것을 비싼 것 앞에

1. **트래커 재대조**(분) → 2. **내 눈 사실검증**(십분) → 3. **렌즈**(시간·토큰)

### 수치를 본문에 쓰기 전에

- 정규식으로 센 숫자는 도구 자신의 출력으로 교차검증한다. 셀 수 있으면 도구가 세게 한다.
- 모든 숫자에 모집단을 같은 문장 안에 붙인다. 모집단이 다른 두 숫자를 나란히 놓지 않는다.
- 실행되지 않는 코드를 결함 경로로 세지 않는다.
- 관측된 출력의 *의미*를 소스에서 확인한다.
- 회귀는 "언제부터"를 `git log -S` 로 도입 커밋을 특정한다.
- 본문에 붙일 터미널 출력은 **실행하는 순간 파일로 캡처**한다. 기억으로 재구성하지 않는다.
- 로컬 재현을 쓰기 전에 그 설정이 업스트림 CI에 이미 있는지 본다. "당신 CI가 지금 그 상태다" 가 "내가 만들어 봤다" 보다 세다.
